매뉴얼이 오해를 부르면 사고가 난다

기술 문서의 독자는 대부분 영어 원어민이 아니고, 문서를 읽는 순간은 대개 바쁘거나 급한 상황입니다. 정비사가 “Check the valve is closed"를 “밸브를 닫아라"로 읽을지 “닫혀 있는지 확인하라"로 읽을지 헷갈린다면, 그건 문서의 결함입니다.

항공 업계는 이 문제를 40년 넘게 하나의 표준으로 풀어 왔습니다. 그게 이번 글의 주제인 ASD-STE100 Simplified Technical English(STE) 입니다. 이 글에서는 STE가 무엇인지, 53개 작성 규칙이 각각 무엇을 요구하는지, 그리고 개발자가 실무에서 어떻게 써먹을 수 있는지 정리합니다.

ASD-STE100 한눈에 보기

STE는 기술 문서 전용 통제 자연어(controlled natural language) 입니다. 일반 영어의 부분집합이라서 원어민에게도 자연스럽게 읽히지만, 쓸 수 있는 단어와 문법이 엄격히 제한됩니다.

항목 내용
시작 1970년대 후반, AECMA Simplified English (Issue 1, 1980)
관리 주체 ASD(유럽 항공우주·방산 산업협회) 산하 STEMG
현행판 Issue 9, 2025년 1월 15일 발행
위상 Issue 8(2021)까지 사양, Issue 9부터 국제 표준
구성 9개 섹션 53개 작성 규칙 + 약 900개 승인 단어 사전
비용 Issue 6(2013)부터 무료, 공식 사이트에서 신청

Issue 9는 새 규칙을 추가하지 않았습니다. 대신 53개 중 31개 규칙의 문구를 다듬었고, 기술 명사·기술 동사 분류를 용어학 표준 ISO 1087-1:2019에 맞췄습니다.

핵심 원리: 한 단어, 한 의미, 한 품사

53개 규칙을 관통하는 원리는 하나입니다. 각 단어는 정해진 하나의 의미와 하나의 품사로만 쓴다. 프로그래밍으로 치면 오버로딩을 금지한 강타입 언어에 가깝습니다.

예를 들어 사전에서 follow는 “뒤따르다"라는 의미로만 승인되어 있습니다. 그래서 “지시를 따르다"라는 뜻으로 쓰려면 follow 대신 obey를 써야 합니다. 마찬가지로 test가 명사로만 승인되어 있다면 동사로 쓸 수 없습니다.

사전에 없는 단어는 무조건 금지일까요? 아닙니다. 부품명·도구명 같은 기술 명사(TN) 와 가공·작업을 뜻하는 기술 동사(TV) 는 해당 분야에서 승인되었다면 쓸 수 있습니다. 즉 STE는 일반 어휘를 통제하고, 도메인 용어는 조직이 관리하도록 열어 둔 구조입니다.

53개 작성 규칙 전체 정리

아래는 Issue 9의 53개 규칙을 섹션별로 한국어로 요약한 것입니다. 공식 원문이 아닌 해설용 요약이므로, 정확한 문구와 예문은 공식 문서를 확인하세요.

Section 1. 단어 (14개)

어떤 단어를, 어떤 의미와 품사로 쓸 수 있는지 정하는 섹션입니다. STE의 뼈대가 여기 다 있습니다.

# 규칙
1.1 사전 승인 단어, 기술 명사(TN), 기술 동사(TV)만 사용한다
1.2 승인 단어는 사전에 지정된 품사로만 쓴다
1.3 승인 단어는 승인된 의미로만 쓴다
1.4 동사와 형용사는 승인된 형태로만 쓴다
1.5 기술 명사 카테고리에 속하는 단어는 쓸 수 있다
1.6 미승인 단어는 기술 명사이거나 그 일부일 때만 쓴다
1.7 기술 명사를 동사로 쓰지 않는다
1.8 회사·업계·분야에서 승인된 기술 명사를 쓴다
1.9 기술 명사를 골라야 하면 짧고 이해하기 쉬운 것을 고른다
1.10 지역어, 속어, 은어를 기술 명사로 쓰지 않는다
1.11 같은 대상에 서로 다른 기술 명사를 쓰지 않는다
1.12 기술 동사 카테고리에 속하는 동사는 쓸 수 있다
1.13 기술 동사를 명사로 쓰지 않는다
1.14 별도 공식 지침이 없으면 미국식 철자를 쓴다

Section 2. 명사구 (2개)

영어 기술 문서의 고질병인 명사 덩어리(noun cluster)를 막는 섹션입니다.

# 규칙
2.1 복합 명사는 명사 3개 이하로 쓴다
2.2 4단어 이상의 기술 명사는 처음에 전체를 쓰고, 짧은 이름을 붙이거나 하이픈으로 명확히 한다

Section 3. 동사 (7개)

시제와 태를 단순하게 제한해 번역과 해석의 갈래를 줄입니다.

# 규칙
3.1 사전에 나온 동사 형태만 쓴다
3.2 허용 형태는 원형, 명령형, 단순 현재, 단순 과거, 단순 미래, 형용사로 쓰는 과거분사뿐이다
3.3 과거분사는 형용사로 쓴다
3.4 조동사를 겹쳐 복잡한 동사 구문을 만들지 않는다
3.5 -ing 형태는 기술 명사이거나 그 수식어일 때만 쓴다
3.6 능동태를 쓴다. 서술문에서 수동태는 행위자를 모를 때만 쓴다
3.7 동작은 명사가 아니라 승인된 동사로 표현한다

Section 4. 문장 (5개)

# 규칙
4.1 짧고 명확한 문장을 쓴다
4.2 문장을 줄이려고 단어를 생략하거나 축약형을 쓰지 않는다
4.3 복잡한 내용은 세로 목록으로 쓴다
4.4 관련 주제의 문장은 연결어로 잇는다
4.5 적용 가능하면 명사 앞에 관사나 지시형용사를 붙인다

Section 5. 절차문 (5개)

“무엇을 하라"는 지시문 규칙입니다. 실무에서 가장 효과가 큰 섹션입니다.

# 규칙
5.1 문장을 짧게 쓴다. 절차문은 문장당 최대 20단어
5.2 동시에 일어나는 동작이 아니면 한 문장에 지시 하나만 쓴다
5.3 지시는 명령형으로 쓴다
5.4 지시를 조건이나 서술로 시작하면 쉼표로 명령과 분리한다
5.5 노트(Note)에는 정보만 쓰고 지시는 쓰지 않는다

Section 6. 서술문 (6개)

시스템 동작이나 원리를 설명하는 글의 규칙입니다. 이 섹션은 번호별 요지를 확인하지 못해 내용 중심으로 정리합니다.

  • 서술문은 문장당 최대 25단어
  • 정보를 논리적 순서로 제시하고, 문단은 주제문으로 시작
  • 한 문단에는 주제 하나
  • 한 문단은 최대 6문장
  • 문장 길이와 구조에 변화를 준다 (6.5)
  • 핵심 용어와 연결어로 흐름을 분명히 한다

Section 7. 안전 지시 (3개)

# 규칙
7.1 위험 수준에 맞는 신호어를 쓴다 (WARNING, CAUTION 등)
7.2 명확하고 정확한 명령이나 조건으로 시작한다
7.3 위험이나 예상 결과를 설명하는 문장을 붙인다

Section 8. 구두점과 단어 수 계산 (7개)

20/25단어 제한을 지키려면 “무엇을 한 단어로 세는가"가 정해져 있어야 합니다. 이 섹션이 그 계산법입니다.

# 규칙
8.1 표준 영어 구두점은 모두 쓸 수 있지만 세미콜론(;)은 쓰지 않는다
8.2 직접 관련된 단어는 하이픈으로 잇는다
8.3 괄호를 쓸 수 있다
8.4 세로 목록에서 콜론은 단어 수 계산상 마침표와 같다
8.5 괄호 안 텍스트는 문장에서 한 단어로 센다
8.6 숫자, 단위, 식별자 같은 요소는 각각 한 단어로 센다
8.7 하이픈으로 이은 단어는 한 단어로 센다

Section 9. 작성 관행 (4개)

# 규칙
9.1 단어 치환만으로 안 되면 문장 구조를 바꿔 다시 쓴다
9.2 각 승인 단어를 올바르게 쓴다
9.3 두 단어를 붙여 구동사(phrasal verb)를 만들지 않는다
9.4 용어와 표현은 항상 일관된 스타일로 쓴다

보충 지침 GR-1 ~ GR-8

53개 규칙과 별도로 문법 보충 지침이 있습니다. 접속사 that, 전치사 with, 대명사 사용, 대명사 this, 거짓 동족어(false friends), 라틴어 약어, 포용적 언어, 소유격을 다룹니다. 예를 들어 e.g., i.e., etc.는 쓰지 않고 for example, that is, 목록으로 바꿉니다.

Before / After 예제

규칙은 예제로 보면 금방 감이 옵니다. 아래는 개발 문서에서 흔히 보는 문장을 STE 스타일로 고친 예입니다.

적용 규칙 Before After
3.6 능동태 The config file is read by the server at startup. The server reads the config file at startup.
3.5 -ing 금지 The service is running in degraded mode. The service operates in degraded mode.
3.7 동사로 표현 Perform a restart of the pod. Restart the pod.
2.1 명사 3개 이하 Update the payment gateway retry policy timeout value. Update the timeout value of the retry policy for the payment gateway.
4.2 축약 금지 Don’t delete the lock file. Do not delete the lock file.
5.2 지시 하나 Stop the consumer and drain the queue. Stop the consumer. Then, drain the queue.
5.4 조건 먼저 Roll back if the health check fails. If the health check fails, install the previous release.
8.1 세미콜론 금지 The job failed; check the logs. The job failed. Examine the logs.
9.3 구동사 금지 Set up the database and carry out the migration. Install the database. Then, do the migration.

restart, drain처럼 사전 승인 단어가 아닌 동사는 조직이 기술 동사(TV)로 등록해야 쓸 수 있습니다. 실무에서는 이렇게 팀 용어집을 함께 관리하는 것이 STE 도입의 핵심입니다.

개발자는 어떻게 써먹을까

STE는 항공·방산 표준이지만, “오해 없이 읽혀야 하고 번역될 수 있어야 하는 글"이라면 어디든 통합니다. 개발 현장에서는 특히 아래 네 곳에서 효과가 큽니다.

  1. 런북과 장애 대응 문서: 새벽 3시에 읽는 문서입니다. 명령형, 한 문장 한 지시, 조건 먼저(5.2~5.4)만 지켜도 실수가 확 줄어듭니다.
  2. 에러 메시지와 UI 문구: 짧은 문장, 능동태, 축약형 금지는 다국어 번역 품질에 그대로 반영됩니다.
  3. API 문서와 README: 같은 대상에 같은 용어를 쓰는 규칙(1.11, 9.4)은 그대로 팀 용어집 운영 원칙이 됩니다.
  4. LLM 프롬프트와 에이전트 출력 스타일: 최근에는 STE 핵심 규칙을 Claude Code 스킬이나 출력 스타일로 주입해 장황한 AI 문장을 줄이는 사례가 늘고 있습니다.

처음부터 900단어 사전을 다 지킬 필요는 없습니다. 아래 핵심 규칙부터 팀 스타일 가이드에 넣어 보세요.

  • 절차문 20단어, 서술문 25단어 제한
  • 능동태, 단순 시제
  • 명사구는 3단어 이하
  • 한 문장에 지시 하나, 조건은 앞에
  • 축약형, 세미콜론, 구동사, 라틴어 약어 금지
  • 하나의 대상에는 하나의 용어

정식 준수가 필요하다면 TechScribe 같은 STE 체커 도구로 승인 단어와 품사를 자동 검사하는 것이 현실적입니다.

마치며

STE의 53개 규칙은 결국 하나의 질문으로 모입니다. “이 문장을 읽는 사람이 다르게 해석할 여지가 있는가?” 이 질문을 습관으로 만들면, 영어든 한국어든 문서의 질이 달라집니다.

공식 문서는 무료로 신청할 수 있으니, 팀 문서 가이드를 만들 계획이라면 원문과 사전을 꼭 한 번 훑어보길 권합니다.
