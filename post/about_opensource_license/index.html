개인 프로젝트들을 GitHub public 레포로 옮기고 정리하다 보니 매번 같은 지점에서 손이 멈췄다. “LICENSE 파일에 뭘 넣지?”

회사 업무에서는 보통 “사내 정책상 GPL 계열 금지” 정도의 규칙만 따르면 됐는데, 막상 내 코드를 공개하는 입장이 되니 고려할 게 생각보다 많았다. 남이 내 코드를 어떻게 써도 되는지, 내가 쓴 의존성 라이브러리의 라이센스와 충돌은 없는지, 나중에 이 코드로 상업 서비스를 하면 문제는 없는지.

이 글은 그 고민을 정리한 기록이다.

⚠️ 이 글은 개발자 관점의 정리이며 법률 자문이 아니다. 상업적·법적 리스크가 큰 결정이라면 반드시 전문가와 상의하자.

0. 먼저 알아둘 것: 라이센스가 없으면 “아무것도 허락하지 않은 것"이다

가장 흔한 오해부터. public 레포에 올렸다고 해서 오픈소스가 되는 게 아니다.

저작권은 코드를 작성하는 순간 자동으로 발생한다. LICENSE 파일이 없는 코드는 기본적으로 All Rights Reserved 상태이고, 다른 사람은 원칙적으로 복제·수정·배포를 할 수 없다. GitHub 이용약관상 다른 사용자가 GitHub 안에서 보고 fork하는 정도는 허용되지만, 그걸 자기 프로젝트에 가져다 쓰는 건 별개의 문제다.

즉,

  • 남들이 자유롭게 쓰길 원한다 → 라이센스를 명시해야 한다.
  • 보여주기만 하고 쓰지는 말라 → 라이센스 없이 두는 것도 하나의 선택이다. (포트폴리오 용도라면 오히려 이게 의도에 맞을 수도 있다.)

1. 큰 그림: 라이센스의 3가지 계열

오픈소스 라이센스는 결국 “내 코드를 가져다 쓴 사람에게 어떤 의무를 지우는가” 의 스펙트럼이다.

계열 핵심 의무 대표 라이센스
퍼미시브 (Permissive) 저작권 고지만 유지하면 거의 뭐든 OK. 소스 공개 의무 없음 MIT, BSD, Apache 2.0, ISC
약한 카피레프트 (Weak Copyleft) 해당 라이브러리/파일 자체를 수정하면 그 부분은 공개 LGPL, MPL 2.0, EPL 2.0
강한 카피레프트 (Strong Copyleft) 이 코드와 결합한 파생물 전체를 같은 라이센스로 공개 GPL v2/v3, AGPL v3

여기에 양 극단으로 퍼블릭 도메인 성격(Unlicense, CC0)과, 오픈소스가 아닌 소스 공개(Source-available) 라이센스(BSL, SSPL 등)가 있다.

“카피레프트(Copyleft)“는 저작권(Copyright)을 비튼 말로, 저작권 제도를 이용해 자유를 강제로 전파시키는 구조를 말한다. “내 코드를 쓰려면 너도 공개해야 한다"는 일종의 바이럴 조항이다.

2. 퍼미시브 계열

MIT License

가장 짧고, 가장 많이 쓰이는 라이센스. 본문이 몇 문단밖에 안 된다.

  • 허용: 사용, 복제, 수정, 병합, 배포, 서브라이센스, 판매 — 사실상 전부
  • 의무: 저작권 표시와 라이센스 문구를 사본에 포함
  • 면책: “있는 그대로(AS IS)” 제공, 보증·책임 없음

언제 쓰나: “누가 어떻게 써도 상관없다, 출처만 남겨줘.” 개인 유틸리티, 샘플 코드, 라이브러리를 최대한 널리 퍼뜨리고 싶을 때. React, Vue, jQuery, Rails 등이 MIT다.

BSD 2-Clause / 3-Clause

MIT와 거의 같은 퍼미시브 라이센스. 3-Clause는 “원저작자의 이름을 파생 제품의 홍보·보증에 쓰지 말 것” 이라는 조항이 하나 더 붙는다. (예전의 4-Clause에는 광고 조항이 있었는데 GPL과 충돌해서 거의 안 쓴다.)

ISC

MIT/BSD-2를 더 간결하게 줄인 버전. npm 초기화 시 기본값이 ISC라 Node 생태계에서 자주 보인다.

Apache License 2.0 ⭐

퍼미시브지만 기업 친화적인 장치가 여러 개 들어간, 훨씬 “법률 문서스러운” 라이센스다. Spring Framework, Kafka, Kubernetes, Android(AOSP 대부분) 등 Java/인프라 생태계의 표준에 가깝다.

MIT와 비교했을 때 추가되는 것들:

  1. 명시적 특허 허여(Patent Grant) 기여자는 자기 기여분에 포함된 특허를 사용자에게 무상으로 허여한다. MIT는 특허에 대해 침묵한다.
  2. 특허 보복 조항(Patent Retaliation) 이 소프트웨어가 특허를 침해했다며 소송을 걸면, 소송 건 쪽의 특허 라이센스가 자동 종료된다.
  3. 변경 사항 고지 수정한 파일에는 수정했다는 사실을 표시해야 한다.
  4. NOTICE 파일 원본에 NOTICE 파일이 있으면 배포 시 그 내용을 유지해야 한다.
  5. 상표권 미허여 프로젝트 이름/로고를 쓸 권리는 주지 않는다.

언제 쓰나: 회사가 엮일 가능성이 있는 프로젝트, 특허 이슈가 신경 쓰이는 도메인(핀테크, 알고리즘, 미디어 처리 등), 혹은 그냥 “기업들이 안심하고 가져다 썼으면 좋겠다"일 때. 개인적으로는 진지한 라이브러리라면 MIT보다 Apache 2.0 을 선호하는 편이다.

3. 약한 카피레프트 계열

“라이브러리 자체는 열려 있어야 하지만, 그걸 가져다 쓰는 쪽 코드까지 강제하지는 않는다"는 절충안.

LGPL (Lesser GPL) v2.1 / v3

  • LGPL 라이브러리를 수정하면 그 수정본은 LGPL로 공개
  • LGPL 라이브러리를 링크해서 사용만 하는 애플리케이션은 자기 라이센스(상용 포함)를 유지할 수 있음
  • 단, 사용자가 라이브러리를 교체할 수 있어야 한다는 조건이 있어서 정적 링크 시에는 까다로워진다

C/C++ 세계에서는 동적 링크 vs 정적 링크가 중요한 쟁점이고, Java에서는 jar를 classpath에 두고 쓰는 건 일반적으로 동적 링크와 비슷하게 취급되어 비교적 부담이 적다. 다만 fat jar/shade로 패키징해서 재배포하는 경우는 한 번 더 따져보는 게 좋다. 대표 예: Hibernate(LGPL 2.1 → 최신 버전은 Apache 2.0으로 전환), MariaDB Connector/J.

MPL 2.0 (Mozilla Public License)

파일 단위 카피레프트. MPL 파일을 수정하면 그 파일만 MPL로 공개하면 되고, 같은 프로젝트의 다른 파일은 어떤 라이센스든 상관없다. LGPL보다 경계가 명확해서 이해하기 쉽다. Firefox, 그리고 BSL로 바뀌기 전의 HashiCorp 제품들(Terraform 등)이 MPL 2.0이었다.

EPL 2.0 (Eclipse Public License)

MPL과 비슷한 모듈/파일 단위 카피레프트. Eclipse 재단 프로젝트, JUnit 5, Jakarta EE 계열에서 볼 수 있다. Java 개발자라면 의존성 리포트에서 의외로 자주 마주친다.

4. 강한 카피레프트 계열

GPL v2 / v3 (GNU General Public License)

  • GPL 코드를 포함하거나 링크한 파생 저작물을 배포하면, 그 전체를 GPL로 소스 공개해야 한다
  • 핵심 트리거는 “배포(distribution)”. 내부적으로만 쓰거나, 서버에서 돌리기만 하고 바이너리를 넘기지 않으면 공개 의무가 발생하지 않는다 → 이게 바로 아래 AGPL이 나온 이유

v2 vs v3 주요 차이

  • v3: 특허 조항 추가 (Apache와 유사한 명시적 특허 허여)
  • v3: 반-티보이제이션(Anti-Tivoization) — 하드웨어가 수정된 소프트웨어 설치를 막지 못하게 하는 조항
  • v3: Apache 2.0과 호환 (v2는 비호환)
  • Linux 커널은 GPLv2 only 라 v3로 올라가지 않았다

“or later” 표기에 주의: GPL-2.0-only 와 GPL-2.0-or-later 는 다르다. 후자는 이용자가 v3 조건을 선택할 수 있다.

💡 Java 개발자를 위한 참고: OpenJDK는 GPLv2 + Classpath Exception 이다. 이 예외 조항 덕분에 JDK 위에서 돌아가는 애플리케이션은 GPL 의무를 지지 않는다. “JDK가 GPL인데 내 앱도 GPL이어야 하나?“라는 걱정은 하지 않아도 된다.

AGPL v3 (Affero GPL)

GPL의 “SaaS 구멍"을 막은 버전. 네트워크를 통해 사용자에게 서비스를 제공하는 것만으로도 소스 공개 의무가 생긴다. 즉, 수정한 AGPL 소프트웨어를 웹 서비스로 돌리면, 그 서비스 사용자에게 소스를 제공해야 한다.

그래서 많은 회사가 사내 정책으로 AGPL 의존성을 아예 금지한다. 반대로 말하면, 오픈소스로 공개하되 대형 클라우드 업체가 그대로 가져가 매니지드 서비스로 팔아먹는 걸 막고 싶을 때 선택하는 라이센스이기도 하다. Grafana, MinIO 등이 AGPL을 채택했다.

언제 쓰나 (내 코드에): “공개는 하지만, 이걸로 서비스를 만들면 너도 공개해라.” 상용 듀얼 라이센스(아래 참고)를 염두에 둔 경우.

5. 양 극단

퍼블릭 도메인 계열: Unlicense, CC0, 0BSD

저작권을 사실상 포기하거나 아무 조건 없이 허락한다. 출처 표기 의무조차 없다. 다만 국가에 따라 저작권 포기 자체가 법적으로 깔끔하지 않을 수 있어서, 코드에는 0BSD나 MIT-0 같은 “조건 없는 퍼미시브"가 더 안전한 선택으로 꼽힌다.

Creative Commons (CC BY, CC BY-SA 등)

문서, 이미지, 블로그 글 같은 콘텐츠용 라이센스다. Creative Commons 측도 소프트웨어에는 CC를 쓰지 말 것을 권장한다 (CC0 제외). 레포 안에 코드와 문서가 섞여 있다면 코드는 MIT/Apache, 문서는 CC BY 4.0 처럼 나눠서 표기하는 것도 방법이다.

Source-available (오픈소스가 아님)

최근 몇 년간 “오픈소스였던 프로젝트가 라이센스를 바꿨다"는 뉴스의 주인공들.

라이센스 요지 사례
BSL (Business Source License) 일정 기간 상업적 사용 제한, N년 후 오픈소스 라이센스로 자동 전환 MariaDB MaxScale, HashiCorp(Terraform 등), CockroachDB
SSPL 서비스로 제공하면 그 서비스 운영에 쓰인 전체 스택까지 공개 MongoDB
Elastic License 2.0 매니지드 서비스로 제공 금지 등 Elasticsearch, Kibana
Commons Clause 기존 라이센스에 “판매 금지” 조건 추가 일부 Redis 모듈 등

소스는 볼 수 있지만, OSI(Open Source Initiative)의 오픈소스 정의를 충족하지 않는다. 이 반발 때문에 Terraform → OpenTofu, Elasticsearch → OpenSearch, Redis → Valkey 같은 커뮤니티 포크가 등장했다. (이후 Elastic과 Redis는 AGPL을 선택지로 다시 추가하기도 했다.)

의존성으로 쓸 때 가장 주의해야 할 영역이다. “예전 버전은 Apache였는데 새 버전부터 바뀌었다"는 경우가 많아서 버전업 시 라이센스도 같이 확인해야 한다.

6. 라이센스 호환성: 섞어 쓸 때의 규칙

내 프로젝트가 여러 의존성을 가질 때, 그 라이센스들이 같이 배포될 수 있는지가 호환성 문제다. 기본 원칙은 단순하다.

결과물의 라이센스는 포함된 것 중 가장 제약이 강한 라이센스의 조건을 모두 만족해야 한다.

대략적인 흐름 (→ 방향으로 포함 가능):

MIT / BSD / ISC
      ↓
  Apache 2.0
      ↓
 LGPL v3 / MPL 2.0
      ↓
    GPL v3
      ↓
   AGPL v3

자주 나오는 케이스:

  • ✅ MIT 코드를 Apache 2.0 프로젝트에 포함 → OK
  • ✅ Apache 2.0 라이브러리를 GPLv3 프로젝트에 → OK
  • ❌ Apache 2.0 라이브러리를 GPLv2-only 프로젝트에 → 비호환 (특허 조항 충돌)
  • ❌ GPL 라이브러리를 MIT/상용 프로젝트에 넣고 배포 → 전체가 GPL이 되어야 함
  • ⚠️ GPL v2-only 와 GPL v3 코드 혼합 → 비호환

방향이 중요하다. 퍼미시브 코드는 카피레프트 프로젝트로 흘러들어갈 수 있지만, 그 반대는 안 된다.

7. 듀얼 라이센싱: 공개와 수익을 동시에

“오픈소스로 공개하고 싶지만, 상업적으로 쓰려는 기업에게는 돈을 받고 싶다"면 듀얼 라이센스 모델이 있다.

  • 커뮤니티 버전: AGPL/GPL — 공개 의무를 지기 싫은 기업은 쓰기 어려움
  • 상용 버전: 유료 상용 라이센스 — 공개 의무 없이 사용 가능

MySQL(GPL + 상용), Qt(LGPL/GPL + 상용), 그리고 여러 AGPL 프로젝트가 이 방식을 쓴다.

단, 듀얼 라이센스를 하려면 내가 전체 코드의 저작권을 보유하고 있어야 한다. 외부 기여를 받는다면 CLA(Contributor License Agreement) 로 기여자에게 권리를 위임받거나, 최소한 DCO(Developer Certificate of Origin, git commit -s) 로 기여의 출처를 확인하는 장치가 필요하다.

8. 그래서 내 레포에는 뭘 붙일까? — 선택 가이드

남들이 이 코드를 가져다 쓰는 걸 원하는가?
├─ 아니오 → 라이센스 없음 (All Rights Reserved), README에 명시
└─ 예
   ├─ 조건 없이 최대한 자유롭게?
   │   ├─ 간단하게 → MIT
   │   └─ 특허/기업 사용까지 고려 → Apache 2.0
   ├─ 내 코드(라이브러리) 수정분만 돌려받고 싶다 → MPL 2.0 / LGPL v3
   ├─ 파생물 전체가 오픈소스로 남길 원한다 → GPL v3
   └─ SaaS로 가져다 쓰는 것까지 막고 싶다 → AGPL v3 (+ 상용 듀얼 라이센스 고려)

개인적인 기준은 이렇다.

레포 성격 선택
블로그 예제, 샘플 코드, 학습용 MIT
재사용 가능한 라이브러리, Spring Boot starter, 유틸 Apache 2.0
언젠가 수익화할 수도 있는 완성형 서비스/툴 AGPL v3 또는 비공개 유지
회사 업무와 조금이라도 겹치는 코드 공개 전 회사 규정 확인부터

마지막 줄이 생각보다 중요하다. 재직 중 작성한 코드의 저작권이 누구에게 있는지는 근로계약서와 취업규칙(업무상 저작물 조항)에 따라 달라진다. 개인 시간에 개인 장비로 만들었더라도 업무 영역과 겹치면 문제가 될 수 있다.

9. 실무 체크리스트

내 코드를 공개할 때

  • 루트에 LICENSE 파일 추가 (GitHub에서 “Add file → LICENSE” 하면 템플릿 선택 가능)
  • 연도와 저작권자 이름 기입 (Copyright (c) 2026 <이름>)
  • README.md 에 라이센스 섹션/뱃지 추가
  • 빌드 메타데이터에도 명시
    • Maven pom.xml: <licenses> 블록
    • Gradle: publishing { pom { licenses { ... } } }
    • npm package.json: "license": "MIT"
    • Python pyproject.toml: license = "Apache-2.0"
  • 소스 파일 헤더에 SPDX 식별자 추가 (선택이지만 권장) 
    // SPDX-License-Identifier: Apache-2.0
  • Apache 2.0이라면 필요 시 NOTICE 파일 작성
  • 커밋 히스토리에 시크릿/사내 정보가 없는지 확인 — 라이센스보다 이게 먼저다. 현재 파일에서 지웠어도 git history에 남아 있으면 공개된다. 필요하면 git filter-repo 나 BFG로 정리하거나, 아예 새 레포로 squash해서 올리자.

의존성 라이센스 점검

공개 전에 내가 쓰는 라이브러리들의 라이센스도 한번 훑어보자.

생태계 도구
Maven license-maven-plugin (mvn license:aggregate-third-party-report)
Gradle com.github.jk1.dependency-license-report
npm license-checker, npx license-checker --summary
Python pip-licenses
통합/CI FOSSA, Snyk, GitHub Dependency Graph, ORT(OSS Review Toolkit)

CI에 넣어서 GPL/AGPL/SSPL 같은 라이센스가 새로 들어오면 빌드를 실패시키는 allow-list 방식으로 운영하면 실수를 미리 막을 수 있다.

마치며

정리하면 이 세 문장이다.

  1. 라이센스가 없으면 오픈소스가 아니다. 공개만 하고 끝내지 말자.
  2. 퍼미시브(MIT/Apache)는 “가져가서 맘대로”, 카피레프트(GPL/AGPL)는 “가져가면 너도 공개”.
  3. 의존성의 라이센스가 내 코드의 라이센스를 제약한다. 특히 GPL/AGPL과 source-available 계열은 버전업 때마다 확인하자.

어떤 라이센스를 고를지 감이 안 온다면 GitHub에서 운영하는 choosealicense.com이 질문 몇 개로 깔끔하게 정리해준다. 라이센스별 허용/의무/제한을 한눈에 보려면 tldrlegal.com도 유용하다.
